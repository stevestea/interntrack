# What you should learn building InternTrack

Checklist. Tick things off as they genuinely click, not when you've merely
typed them once. The goal is being able to explain each one out loud in an
interview.

---

## 1. Python beyond syntax

- [ ] Modules and packages — why `app/` has an `__init__.py`, how imports resolve
- [ ] Exceptions — `try`/`except`, and the harder judgment call of when NOT to
      catch (swallowing an error hides the bug that caused it)
- [ ] Context managers — what `with open(...)` actually guarantees
- [ ] Comprehensions over manual loops
- [ ] Type hints — not required, but they make review far easier
- [ ] Standard library you'll actually touch: `csv`, `pathlib`, `datetime`,
      `collections.Counter`

## 2. Relational data modeling — the highest-value thing here

- [ ] Primary keys, foreign keys, and what "referential integrity" buys you
- [ ] Normalization: why `companies` is its own table instead of a string column
- [ ] `SELECT` / `WHERE` / `JOIN` / `GROUP BY` / `ORDER BY` written by hand,
      not just generated by an ORM
- [ ] UNIQUE constraints and indexes — why the DB enforces dedup, not Python
- [ ] ORM concepts: models, sessions, relationships
- [ ] The **N+1 query problem** — you will hit it on the list page; recognizing
      it by name is a real interview signal

## 3. How the web actually works

- [ ] HTTP methods and status codes — what makes something GET vs POST
- [ ] Routing and URL parameters
- [ ] Jinja templates, and why logic doesn't belong in them
- [ ] Forms and the POST-redirect-GET pattern (and the double-submit bug it fixes)
- [ ] Returning JSON vs HTML from the same data

## 4. Data analysis — your BAT coursework, applied

- [ ] pandas: `DataFrame`, `groupby`, `merge`, `value_counts`
- [ ] **When to aggregate in SQL vs in pandas** — this is a genuine engineering
      judgment, not a style preference. SQL for large filtering/joining, pandas
      for shaping and stats.
- [ ] Data cleaning: normalizing text, deduplication, handling missing values
- [ ] Choosing a chart that answers the question rather than one that looks busy

## 5. Engineering practice — what separates a student repo from a real one

- [ ] Git: small commits, messages that say *why*, `.gitignore` hygiene
- [ ] pytest: fixtures, arrange–act–assert, and deciding what's worth testing
- [ ] CI with GitHub Actions — tests running on every push
- [ ] Dependency pinning and virtual environments
- [ ] **Reading a traceback properly** — bottom line first, then the file and
      line. Most beginners skim it and start guessing. Don't.
- [ ] Debugging by forming a hypothesis and testing it, not by changing things
      at random until the error moves

## 6. Talking points you'll own by the end

These are yours to defend in an interview. Each one is a decision with a
trade-off, which is exactly what interviewers probe for.

- [ ] Why ingestion is decoupled from storage (a broken scraper degrades to
      manual import instead of an outage)
- [ ] Why `status_events` is append-only instead of one overwritten column
      (you can't compute response time from a value you overwrote)
- [ ] Why `companies` is normalized (string columns silently split your analytics)
- [ ] What you'd do differently with more time, and what you deliberately left out

---

## The honest ranking

If you only truly absorb three things from this project, make them:

1. **Relational data modeling.** It transfers to every backend and data job.
2. **Reading tracebacks and debugging methodically.** It's the difference
   between being stuck for 10 minutes and stuck for 3 hours.
3. **Testing.** Almost no student projects have tests. Yours will.
